# M11 · 岗位画像层（Role Profile Layer）

> 2026-10-29 | Issue #31 | 承接「一个岗位怎么处理」
>
> 数字一律以 `role list` / `role db` / `role chain --check` 的实跑输出为准，正文不抄第二份。

## 0. 一句话

**行业单元回答"这行有没有"，岗位画像回答"这个岗位能不能真上手干活、缺什么"。**

前面 14 个行业单元、全部注册岗位，注册表里每个岗位只有一行 `name / prefix / keywords` ——
那只是**路由信号**，不是岗位本身。M11 补齐岗位的**评估表 + 可执行工序**，让"细分到岗位"这件事
在数据上真的成立：行业当前用不上没关系，**画像先立起来，就绪度如实显示还差什么**。

## 1. 六维评估表（核心交付物）

每个岗位一张卡，六个维度，缺一维就扣分（不报错）：

| 维度 | 回答什么 | 关键字段 |
|------|----------|----------|
| ① 岗位分析 analysis | 这岗位到底在干什么 | mission / deliverables / inputs / outputs / kpis |
| ② 岗位画像 persona | 谁来干、什么脾气、什么边界 | seniority / mindset / tone / decision_rights / constraints |
| ③ 插件封装 plugin | 能不能装起来 | bundle / tools / mcp_categories / artifacts |
| ④ 工作流 workflow | 从诉求到交付的工序 | templates / default_flow / activation |
| ⑤ 利益链条 stakeholders | 上下游、谁受益、谁阻碍 | upstream / downstream / beneficiaries / blockers / incentives / risk_notes |
| ⑥ 核心能力 capability | 会干什么、干到什么程度 | core / tools / knowledge / soft / **scoring(0-5)** |

能力评分固定五维，便于横向可比：
`domain 领域深度 0.30 / tooling 工具熟练 0.20 / judging 判断力 0.20 / execution 执行力 0.15 / comms 沟通交付 0.15`

## 2. 双源分离（为什么这么拆）

```
data/role-profiles/<unit>.yaml   人写，慢变，六维评估（事实与判断）
data/workflow-templates/*.yaml   通用工序模板（可复用资产）
data/rolecards/<unit>.yaml       机器渲染产物（提交入库，可 diff、可 review、可被别的 runtime 读）
```

- **画像基线**是人写的：使命、边界、利益链条这类东西不能靠算法编。
- **岗位卡**是渲染出来的：把「注册表岗位事实 × 画像基线 × 工作流模板 × 上游技能包」合成一份可执行卡。
- 落盘而不是每次现算：n8n、纯代码、别的 Agent 都能直接读这份 YAML，不用装 Python。

## 3. 就绪度（能不能上手，一个数说清）

```
score = 100 × ( 0.35·六维覆盖 + 0.25·能力均分/5 + 0.20·工作流可执行 + 0.10·插件就绪 + 0.10·利益链条清晰 )
评级  A≥75 可直接跑通 / B≥55 可跑需人工兜底 / C≥35 仅能问答 / D<35 只有骨架
```

关键是**给缺口**：不是给个分数就完事，而是直接告诉你"`capability.scoring` 缺 judging"、
"步骤 inspect 缺 verify"。行业能不能用，一眼有数，也一眼知道下一步补哪。

口径见 `data/rolecard-schema.yaml`（权重/分档/字段清单都在数据里，改口径不用改代码）。

## 4. 工作流：模板 + 覆盖 → 三种落法

岗位不重写流程，只写**要改的那几步**：

```yaml
workflow:
  default_flow: standard-delivery
  templates:
    - template: standard-delivery      # 六段式：接单→取上下文→主作业→自检→交付→交接
      id: wf-architecture
      name: 架构方案流
      default: true
      override:
        steps:
          execute:                     # 按 id 覆盖，模板其余步骤自动继承
            name: 方案设计
            playbook: 先列约束与非功能要求，再出候选方案，最后给出推荐与代价
            verify: [每项关键选择都写明了代价]
```

导出形态（同一份数据，`runtime: agent | n8n | code`）：

```bash
python3 src/hanghang/cli/main.py role playbook architect --format text   # 人读/Agent 照着干
python3 src/hanghang/cli/main.py role playbook architect --format json   # 编排引擎消费
python3 src/hanghang/cli/main.py role playbook accountant --format n8n   # n8n 节点清单（不含凭据）
python3 src/hanghang/cli/main.py role playbook accountant --format code  # 纯代码桩
```

现有模板：`standard-delivery` / `fast-answer` / `review-gate` / `code-check` / `n8n-receipt-to-sheet`。

## 5. 接进主链路（不是摆着看的表）

| 接点 | 怎么用 | 不接会怎样 |
|------|--------|-----------|
| M1 路由 | 岗位关键词得分 `1.5 × activation.weight`，权重写在画像数据里 | 路由知识散落在 `router.py` 的硬编码优先级里 |
| M10 装配 | 岗位卡渲染成**层A静态块**（同岗位同版本恒定） | Agent 只带一个 `[架构]` 前缀，不知道岗位使命/边界/工序 |
| CLI `role show` | 一次看全六维 + 就绪度 + 缺口 | 要翻好几个文件拼图 |
| `role playbook` | 直接拿分步工序跑 | 每个行业重新发明流程 |

**缓存安全**：岗位卡进层A，内容只由画像数据决定。实测同岗位不同 session 的 `cache_key` 一致
（`assemble` 两次同岗位 → 同 cache_key；加 `--no-rolecard` → 不同 cache_key），不破坏 M10 的缓存隔离铁律。

## 6. 数据驱动：新增行业/岗位怎么做

```bash
# 1) 在 data/role-profiles/<新unit>.yaml 写六维画像（缺项也行，会进缺口清单）
# 2) 渲染
python3 scripts/gen_rolecards.py --unit <新unit>
# 3) 看就绪度、按缺口补
python3 src/hanghang/cli/main.py role list --unit <新unit>
```

不改一行 Python。这也正是"很多行业当前用不上，但架构上可以了"的落法：
**先让岗位有卡、有评分、有缺口，行业成熟时直接补数据。**

## 7. 上游借鉴（vendor，只读）

`vendor/upstream/knowledge-work-plugins` 是 anthropics/knowledge-work-plugins 的快照（Apache-2.0）。
借的是**形态**——"岗位 → 技能包 → 工作流命令"的打包方式，以及一批可直接挂载的技能说明文件
（如 `engineering/skills/architecture/SKILL.md` 被写进 `architect` 的 `plugin_artifacts`）。

不借的是**运行期**：不加载上游 `.mcp.json`、不执行上游命令、不引入上游 Node 依赖。
上游只是离线渲染的数据源，快照 commit 见 `vendor/upstream/knowledge-work-plugins/UPSTREAM.md`。

## 8. 演进：从画像到流程资产

当前岗位卡已能导出 `agent / n8n / code` 三形态骨架。下一步（未做，留作方向）：

1. **流程库**：把同一工序组合（如"合同审查流"）抽成可跨行业复用的流程资产，岗位只引用
2. **评测跑分**：用岗位卡的 `kpis` 定义离线评测集，把就绪度从"写得全不全"升级为"跑得对不对"
3. **画像漂移检测**：岗位卡入库后，画像基线与渲染产物的一致性由 `gen_rolecards.py --check` 在 CI 把关（已做）

## 9. M11.1 · 利益链条归一：只存类，公司靠查（2026-10-29 追加）

### 9.1 病根

画像要通用，链条就不能写死成"某某钢材加工厂"。
写死一家公司，换一个客户整张卡就废了，也没法跨行业复用——但链条又必须说清"上游是谁"。
这条线只能这么切：**链上写行业类目，具体公司靠索引现查，名录不进仓库。**

### 9.2 三层结构

| 层 | 存什么 | 存在哪 | 谁维护 |
|----|--------|--------|--------|
| 类目 class | `钢材加工` `品牌方` `用人部门` `用户` | `data/industry-classes.yaml` | 人写，可跨行业共享 |
| 索引 index | 怎么查到具体公司（来源 + 查询式） | 同上，随类目一起声明 | 人写，只写检索方式 |
| 公司 records | 具体企业名录、客户档案 | **不在本仓库** | CRM / 企业名录 / ATS / 内部主数据 |

类目带 `kind`（制造 / 服务 / 渠道 / 机构 / 内部组织 / 需求方 / 阻碍 / 接口 / 单元），
`index` 可空——**接口、阻碍、内部组织这类本来就没有"公司索引"**，不要求接。

```yaml
classes:
  钢材加工:
    kind: 制造
    index: {source: 企业名录, query: ["钢材{加工|剪切|开平}", "金属材料加工"]}
  跨岗口径不一致: {kind: 阻碍, index: null}   # 原因不是实体，不该有公司索引
```

### 9.3 归一规则

引用只有四种落点，全部由 `rolecard/chain.py` 判：

- `industry_class`：词表里的类目，带 `ref` 和 `index`
- `interface`：接口/渠道类目（合并门禁、发布渠道、运维），本来就不落具体主体
- `role`：岗位引用，落到 `unit + role`。**跨单元就写清哪个单元**，不许拿单元 id 当岗位糊过去
- `unregistered`：未登记 → 直接报错，逼你先登记类目而不是随手造同义词

叫法收敛由 `aliases` 管：`最终用户`/`用户（人）` → `用户`；`岗位产物口径不一致导致返工` → `跨岗口径不一致`。
归一后 `value` 是统一说法，`raw` 保留原文可追溯。

### 9.4 守门

```bash
python3 src/hanghang/cli/main.py role chain architect --unit dongjiagoushi   # 看归一结果
python3 src/hanghang/cli/main.py role chain --check                          # CI 守门
python3 src/hanghang/cli/main.py role chain --class 钢材加工                  # 类 → 被谁引用 + 怎么查
```

`--check` 的判定（已接进 PR 与合并门禁的 `.cnb.yml`）：

| 情况 | 级别 | 为什么 |
|------|------|--------|
| `XX有限公司` / `某某厂` / `XX集团` | **error** | 把具体公司存进来了，换客户就废 |
| 类目没在词表登记 | **error** | 放任同义词扩散，三个月后没人认得清 |
| 类目 `index: null` 且本该可查 | warn | 如实说"还没接索引"，不装 |
| 引用了别的单元的岗位 | warn | 跨域复用是允许的，但要看见 |

当前状态：0 error / 0 warn —— 全量归一完成，索引该接的已接，没接的本来就不该接（岗位数见 `role chain --check` 输出）。

### 9.5 落到列表和索引，而不是落到库

`role chain --class <类目>` 就是那份"列表"：这个类被哪些岗位、哪个字段引用，查具体公司走哪个来源。
真正做行业插件时，从类目反查公司是**运行时检索**，不是仓库里的数据。

```bash
$ role chain --class 用户
行业类: 用户  [需求方]
  索引: 会员主数据 → 用户画像与分群
  说明: 只存检索方式，不存公司名录
  被引用: 58 处
```

### 9.6 对岗位卡的影响

- 岗位卡新增 `chain_refs`：归一后的链条引用（类目带 `ref/index`，岗位带 `unit`），与六维原始字符串并列落盘
- `to_context_block()` 的上游/下游改用统一说法注入（原文保留在 `six_dims` 里，不丢信息）
- 就绪度口径**不变**：归一是表述规范化，不虚增分数
