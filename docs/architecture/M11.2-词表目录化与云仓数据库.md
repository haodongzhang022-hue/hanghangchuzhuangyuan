# M11.2 · 词表目录化 · 数据库形态 · 云仓检索

> 2026-10-29 | Issue #31 | 承接「肯定不能一个 yaml 装啊」

## 0. 一句话

一个 YAML 装全部行业类，**查不了、join 不了、也没法分工维护**。
拆成三层各司其职：**仓库里的目录（谁在维护什么）→ 数据库结构（怎么 join、怎么统计）→ 云仓检索（一句话怎么找到它）**。

## 1. 病历：一个 YAML 到底哪里不对

M11.1 把 62 个行业类塞进 `data/industry-classes.yaml` 一个文件。当时就自认了三条毛病，
这次是把它们当真修掉：

| 病 | 症状 |
|---|---|
| 没法分工 | 谁想加一个类目都得改同一个文件，必冲突 |
| 没法溯源 | 看到一个类目，不知道该动哪个文件、谁负责的域 |
| 没法查 | 想"这个类被哪些岗位写在哪个字段"只能写代码遍历，SQL 都 join 不了 |

## 2. 第一层：目录化（`data/industry-classes/`）

按**域**拆，每个文件只装一个 kind 家族：

```
data/industry-classes/
├── supply.yaml       4 条   制造 / 货品与流通 / 资源（上游供货材料）
├── demand.yaml      16 条   需求方 / 需求 / 输入（客户、用户、业务方）
├── delivery.yaml     4 条   接口 / 渠道（合并门禁、发布渠道，没有公司主体）
├── internal.yaml    16 条   内部组织 / 岗位类（用人部门、团队角色）
├── institution.yaml  2 条   机构（医院、学校、监管）
├── blocker.yaml     15 条   阻碍因素（原因侧，将来应独立成层）
└── unit.yaml         5 条   行业单元（跨单元引用的双向入口）
```

`data/industry-classes.yaml` 变成**汇总入口**，只放全局口径（公司形态标记、跨叫法别名）
和 `!include` 引用。新增类目改对应域文件，不要去动汇总文件。

`!include` 只支持两种写法，刻意不做变量替换和条件 —— 那是模板引擎和数据库的活：

```yaml
whole: !include upstream.yaml          # 整文件并入
merge: !include [a.yaml, b.yaml]       # 逐文件并入并合并
```

实现上踩过一个坑，记在这里免得再踩：PyYAML 的 `construct_object` 以**节点对象**为 key 做缓存，
父子文档里 value 相同的标量会被当成同一个节点，于是 `classes: !include x.yaml`
（x.yaml 里也是 `classes:`）会解析成 `{classes: {classes: ...}}` 错位嵌套。
所以 `yamlload.py` 用 `yaml.compose` 拿节点树、自己在 Python 里合并，父子缓存完全隔离。

**溯源**：`IndustryClassIndex.sources` 记住每个类目声明在哪个文件。`role classes` 直接打出来。

## 3. 第二层：数据库形态（`data/db/`）

不是连库，是那套**结构**：

```sql
industry_class    类目表（name / kind / label / is_entity / source_file）
class_alias       别名表（同一个东西三种叫法，收敛到一个 class_name）
class_index_src   索引源表（source + query_expr：这个类去哪个系统怎么查）
role_chain_ref    岗位引用表（哪个岗位的哪个字段引用了哪个类）
```

四张表能 join，于是原来要写代码遍历的问题变成一句 SQL：

```sql
-- 用户这个类被哪些岗位、写在哪个字段
SELECT unit_id, role_name, field FROM role_chain_ref WHERE class_name = '用户';
-- → 58 行

-- 哪些实体类目还没接检索源（欠账清单）
SELECT name FROM industry_class c
WHERE is_entity = 1 AND NOT EXISTS (SELECT 1 FROM class_index_src s WHERE s.class_name = c.name);
```

**没有公司名录表，这是故意的。** 企业名录、客户档案、供应商台账住在 CRM / 企业名录 / ATS /
内部主数据里，`class_index_src` 只记"去哪个系统用什么查询式查"。把名录塞进仓库既不合规也不通用 ——
这条和 M11.1 的"公司不进画像"是同一件事，只是换了个位置守。

产物由 `scripts/export_class_db.py` 从域文件生成（DDL / SQL / 数据字典 README），
CI 里 `--check` 拦住"改了类目忘了重导出"。

## 4. 第三层：云仓检索（`rolecard/cloudstore.py`）

Agent 干活时问的是「这个行业的上游大概是干嘛的」——这句话没有精确类目名，需要**语义检索**。
CNB 知识库（云仓）干这件事：由 `main.push` 的 `knowledge:update` 重建，这里只读。

三条取舍：

1. **只读不写**。入库交给流水线，不在代码里再实现一遍，避免两套口径打架。
2. **失败即降级**。没 token / 没网 / 接口挂了，一律退回本地词表扫描，主流程不受影响。
   云仓是加速层，不是依赖。
3. **只回命中类目 + 分数 + 来源**，不回传整段文档 —— Agent 要的是"往哪查"，不是一篇散文。

本地兜底也做了裁剪：单字类目和「单元」「岗位类」不参与自然语言命中，
否则「开发」「产品」这种满地都是的词会把真答案淹掉。

## 5. 三个入口

```bash
python3 src/hanghang/cli/main.py role classes              # 词表怎么分布在哪些文件
python3 src/hanghang/cli/main.py role classes --unregistered  # 实体类目还差哪些检索源
python3 src/hanghang/cli/main.py role search "钢材加工的上游"   # 云仓 + 本地，回命中类目
python3 src/hanghang/cli/main.py role chain --class 用户      # 这个类被谁引用、怎么查
python3 scripts/export_class_db.py                          # 重生成 data/db/
```

## 6. 没做的（说清楚）

1. **DDL 是 SQLite 语法**。PostgreSQL 只需把 `AUTOINCREMENT` 换成 `SERIAL`/`IDENTITY`，
   但真接库还要处理迁移、权限、多租户，这层没做。
2. **`class_index_src` 只是声明**，没有真的执行检索。接 CRM / 企业名录是下一步，且需要凭据 ——
   凭据不该进仓库，这条线我留空了。
3. **`blocker` 还在同一套类目体系里**。它本质是"原因"不是"实体"，虽然 `is_entity=0` 标了，
   但等真有阻碍因素库时应该独立成一张表，不然语义会糊。
4. **云仓返回的相似度分数偏低**（0.00x 量级），因为知识库里行业类的密度还很低。
   类目文档补齐后会好转，但那是知识库内容问题，不是检索层问题。
