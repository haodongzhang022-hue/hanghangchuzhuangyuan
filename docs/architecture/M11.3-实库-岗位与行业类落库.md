# M11.3 · 实库：岗位 / 行业类 / 利益链条落库

> 2026-10-30 | Issue #31 | 承接「这个起码有库的结构吧，后面买个服务器能直接用」

## 0. 一句话

M11.2 交的是**图纸**（DDL 文本），不是**房子**（能开的库）。
这次把库真建出来：`data/db/hanghang.db`，654 KB、3500 行、能开能查能 join，
换服务器只需换方言 —— `data/db/00-schema.postgresql.sql` 同表同列。

## 1. 病历：空着的那层到底缺什么

| 当时说的 | 真实状态 |
|---|---|
| 「四张表能 join」 | 只有 `.sql` 文本，仓库里没有一个 `.db` |
| 「DDL 是 SQLite 语法」 | 通了但没人执行过，也没读回来过 |
| 「换 PG 改 AUTOINCREMENT 就行」 | 手改必然漂移，没有双方言单源 |
| —— | 岗位画像（六维/工作流/评分/就绪度）根本没进库，只在 YAML 里 |

## 2. 建了什么

```bash
$ python3 scripts/build_role_db.py
已重建 data/db/hanghang.db（664 KB）
  industry_class            62   类目
  class_alias               31   别名（同义词收敛）
  class_index_src           22   索引源（去哪个系统怎么查公司）
  role_chain_ref           357   链条引用（类目/接口/岗位三类落点）
  industry_unit             14   行业单元
  industry_role             50   岗位清单（前缀/触发词/简介）
  role_profile              50   画像元信息（使命/资历/语气/包名）
  role_profile_item       1587   六维清单字段，一条一行
  capability_score         250   能力评分（五维 0-5）
  workflow                  50   工作流（模板 + 触发 + 交接）
  workflow_step            244   工序（runtime=agent|n8n|code）
  step_assertion           579   前置/产出/验收断言
  plugin_artifact           53   可挂载技能文件
  readiness                 50   就绪度（分数/评级/缺口）
  schema_version             1   结构版本 + 构建溯源
  schema_definition         96   结构自述（表→列，随库走）
```

三条硬约束（不是风格问题）：

1. **列表型字段一条一行**。交付物/KPI/上游/验收都进 `role_profile_item` 和
   `step_assertion`，所以「哪些岗位把『用户』写进了受益方」是一句 SQL，不是遍历代码。
2. **数值以文本存、读写统一 float**。SQLite 与 PG 的类型亲和性不同，同一份数据
   在两边行为要一致；这层差异由代码吸收，不由使用者记。
3. **没有公司名录表**。企业名录住 CRM / ATS / 企业名录 / 内部主数据，
   库里只存 `class_index_src`（来源 + 查询式）。公司名录进仓库既不合规也不通用。

## 3. 结构单源，双方言

`rolecard/schema_sql.py` 里表定义只写一份（`_TABLES` / `_INDEXES`），
渲染成两种方言。库建表、DDL 导出、测试里的列名断言全从这一份走 ——
改表只改一处，不存在「库里改了、DDL 没改」的漂移。

```
sqlite      id INTEGER PRIMARY KEY AUTOINCREMENT
postgresql  id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

## 4. 一致性：库不许静默落后于仓库

`scripts/build_role_db.py --check`：建库 → **读回来** → 与内存里的画像卡逐字段比。
比对前两边都规范化（dict 键排序、列表按内容排序、空值/缺省等价），
因为「行顺序」「空列表 vs 没有行」不是语义差异。

所以 `data/db/*.db` 不进版本库（`.gitignore`）：重建是确定性、秒级的，
把二进制塞进 git 只会得到看不见的 diff 和合不了的冲突。产物形态（双方言 DDL、
类目 SQL、数据字典）进库，随时 rebuild。CI 的 PR 与合并门禁两处都会跑 `--check`。

## 5. 三个入口

```bash
python3 src/hanghang/cli/main.py role db                  # 库里有哪些表、多少行
python3 src/hanghang/cli/main.py role db --build          # 手动重建
python3 src/hanghang/cli/main.py role db --sql "..."      # 只读查询
python3 scripts/build_role_db.py --check                  # 库与数据是否一致（CI）
python3 scripts/build_role_db.py --stats --json           # 给流水线消费
```

库能被真用，不只是被数行数：

```sql
-- 哪些岗位把「用户」写进了链条
SELECT unit_id, role_name, field, ref_kind FROM role_chain_ref WHERE class_name='用户';

-- 哪些实体类目还没接公司检索源（欠账清单）
SELECT name FROM industry_class c WHERE is_entity=1
  AND NOT EXISTS (SELECT 1 FROM class_index_src s WHERE s.class_name=c.name);

-- 工序最长的岗位（编排复杂度）
SELECT unit_id, role_name, count(*) n FROM workflow_step GROUP BY 1,2 ORDER BY n DESC;
```

## 6. 今后真买服务器时，要动的只有三处

1. **方言**：`schema_sql.ddl("postgresql")` 已经产出，机械替换不需要手改。
2. **连接**：`dbstore` 里写死的 `sqlite3.connect` 换成 PG 驱动；SQL 里没有
   SQLite 方言特性（无 `INSERT OR REPLACE`、无 `PRAGMA` 依赖读写路径），
   唯一要动的是 `schema_definition` 的 upsert 写法。
3. **凭据**：连接串走环境变量，不进仓库（与 `cloudstore` 的 CNB_TOKEN 同一规矩）。

## 7. 没做的（说清楚）

1. **没有迁移框架**。现在策略是「全量重建」，数据量小（664 KB）所以成立；
   真开始积累业务写入（交班记录、检索日志）时必须上 Alembic 或等价迁移，
   否则重建会丢写入。这条别拖。
2. **仍是单机 SQLite**。并发写弱，够跑 CLI 与离线渲染；多租户 / 并发服务要 PG。
3. **没有查询层抽象**。`role db --sql` 直接透传，谁都能写跨表 SQL；
   将来若对外暴露，需要一层白名单视图，别让使用者依赖表结构。
4. **`class_index_src` 还是声明**。库里能看出「该去 CRM 查」，但仍不执行检索 ——
   接检索要凭据，凭据不进仓库。
