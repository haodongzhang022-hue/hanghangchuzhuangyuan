## 0. 一次说清：这层到底做什么

我们不是要造"又一个岗位 agent"，而是要造**把各行业/岗位单元串起来的「路由编排总层」**。

用一个类比讲透：

- `dongjiagoushi`（架构团队）= 一套「设计和开发的公司 + 各岗位」的聚合体，内部实现了**多 agent 之间的协作与交接**（跨 agent 切换、协作、交接）。
- 现在要做的，是把「dongjiagoushi 这类**行业单元**」当作一个个**原子/单位**，横向扩展到游戏开发等多个行业，并在它们**之上**再叠一层：**行业切换、路由、交接、交叉**。
- 目标是：用户不手动切模式，由系统**自动识别当前该路由到哪个行业/岗位单元**，并把复合型的跨界诉求正确拆分与交接。

```
                          ┌───────────────────────────────┐
     更高一层架构（本仓库） │ 行业路由编排层(通用能力)         │
     行业切换/路由/交接/交叉 │ - 自动识别当前行业/岗位           │
                          │ - 跨行业复合任务拆分/交接          │
                          └───────────────┬───────────────┘
                 ┌──────────┬──────────────┼──────────────┬─────────┐
                 ▼          ▼              ▼              ▼
         [dongjiagoushi]  [游戏开发]     [行业N]        [行业M]
          行业单元=原子   行业单元       行业单元        行业单元
          (内部已做多agent协作交接)
```

---

## 1. 定位与边界

**做**（通用能力层 / 本仓库主线）：
- 行业/岗位级的路由与调度编排（把各行业单元串成一个大系统）
- 自动识别行业与岗位，无需用户切换模式
- 跨行业/跨岗位复合任务的拆分、交接、交叉调度
- 稳定前缀的提示词 / 会话策略，保证路由一致性

**不做 / 属其他项目（不在本仓库混）**：
- 电子书检索 → 已归档，归 `sousuozengqiang` 项目
- 单个行业单元的内部岗位细节（如 dongjiagoushi 内的岗位协作），那是行业单元自己的事

## 2. 用户对「反向追问」的补充 → 需求落点

> 架构·产品曾提 5 个反问；用户已针对「通用能力」口径补充，落点如下。

### 追问1：先跑通的「1 个」业务场景是哪个？
**用户补充**：不是单个业务单，而是一个「行业单元」样例。以 `dongjiagoushi`（架构团队）为一个成熟行业单元作参照；游戏开发在另外库。我们要横向覆盖多个行业/岗位，让其更全面，然后做自动路由。

> ✅ **落点（给总师）**：MVP = 打通「把 dongjiagoushi 作为一个可路由行业单元，接入本路由层，并验证自动识别 → 正确路由 → 不切换模式完成对接」这一条链。也就是先证明**路由总层能收编一个现成的行业单元**。

### 追问2：秘书交接卡的具体用例/能力清单在哪？
**用户补充**：例子在如 `dongjiagoushi` 这类其他仓库（它完成了多 agent 协作交接，覆盖了多 agent 切换和协作）。

> ✅ **落点（给总师）**：交接卡的"能力样本"以 `dongjiagoushi` 为参照物；本层不重新臆造岗位细节，而是把 `dongjiagoushi` 的既有协作交接能力当成一个被路由的**行业单元**来抽象。

### 追问3：人工兜底层级？
**用户补充**：人工尽量只在**开头和结尾**；中间尽可能全自动、不依赖人类。出现人工越多 = 自动化越低。优先机制与自动化。

> ✅ **落点（给总师）**：人工只留在两头（需求确认 / 最终交付复核），中间编排/路由/交接全部自动。

### 追问4：判定"能力足够高、可转生态整合"的量化标准？
**用户补充**：正常使用不切模式、不影响缓存命中的情况下，能完成**多行业**架构师/开发人员等岗位切换；能形成**同时 2 个甚至多个岗位的复合型 agent**；可**动态加跨界能力**。

> ✅ **落点（给总师）**：
> - 量化信号①：同一 session 内不切模式、缓存命中不失效，即可完成跨行业/岗位切换；
> - 量化信号②：能并行/叠加形成多岗位复合 agent；
> - 量化信号③：可动态挂载新的跨界能力而无需重构。
> 满足上述即视为"能力足够高"，触发向生态整合演进。

### 追问5：交互形态 / 数据源？
**用户补充**：这是一套系统，可在 cnb.cool 与 deepseek harness 这类生态里，以 agent 协作模式运行，形态类似 dongjiagoushi（agent 互相协作交接）。

> ✅ **落点（给总师）**：首个交互形态=agent 协作/路由调用（API/编排式），前端仅做聚合+可视化，为将来生态整合预留多种调用形态。

## 3. 关键设计约束（转给架构·总师）

1. **提示词前缀稳定性**：路由会触发不同行业/岗位的提示词差异。要求：
   - 同一 session 内提示词前缀尽量稳定、不随对话变化；或
   - 把不同上下文切到**不同对话**，各自维持稳定前缀。
2. **路由一致性**：不切模式的背后 = 有稳定可判的路由信号 + 稳定的 prompt 前缀，避免每次会话漂移导致缓存命中失效。
3. **收编行业单元为原子**：行业单元（如 dongjiagoushi）是路由层的被管对象，内部细节不重新实现，只做其能力描述 + 触发时机 + 路由地址入库。
4. **复合跨界**：支持一个诉求拆成多行业/多岗位子任务，并支持多岗位复合 agent 的并发/叠加。
5. **人工两头化**：只在开头（需求澄清）与结尾（复核交付）留人工，中间自动。

## 4. 给架构·总师的设计提问（供输出用，不作预设立场）

- 行业单元的"可路由描述"用什么 Schema 统一入库？（能力/触发词/路由地址/协作接口）
- "自动识别路由"的判定信号来自哪？（意图→行业→岗位？是否需要每单元提供路由索引）
- 多岗位复合 agent 的并发模型：进程级叠加 还是 单元间交接串联？各自缓存如何隔离/共享以保证命中？
- 稳定前缀的实现：固定全量前缀 还是 分行业会话前缀 + 跨会话路由？
