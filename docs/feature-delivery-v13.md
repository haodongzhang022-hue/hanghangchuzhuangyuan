# 功能交付 v13 · 补全与视角分离（M11 第三轮）

**来源**：用户在 PR #29 的口径纠正 ——

> "按交税时候看哪些职业占比，可能就发现之前没统计到的职业，比如主播、陪玩。
> 行业、产出，这些不是用不同轴，而是不同视角看，尝试把职业补全，多个方向的补的
> 都是职业，只是一个角度的不全。军队、采矿工这种难以付费和交付的也要，只是分类的
> 时候把他们放考虑的维度不一样 —— 不是他们直接付费和交钱交付，而是这类人群有什么
> 需求、产出的东西怎么卖给这些人群；他们本身职业也是有价值的，值得被分析，
> 所以不该被直接忽略。他们的人群画像影响着市场，值得被存着。"

## 一、上一版错在哪

上一版把两件事压成了一个判断："**能不能直接向终端用户收费**"。

一旦用这个过滤器筛，会同时丢掉两类人，而理由完全不同：

| 丢掉的 | 真实原因 | 上一版的处理（错） |
|---|---|---|
| 主播 / 陪玩 / 电竞 / 骑手 | 不是"付不起"，是**口径根本没扫到**（挂在互联网信息服务下，不独立成行） | 只登记了"新媒体运营"，整个行业看不见 |
| 军人 / 消防 / 矿工 / 船员 | 不是"不值得"，是**付费方不是终端用户**（财政 / 项目款 / 实物产出） | 塞进 `evaluated`，从此不进分母、不入画像 |

两种错混在一起，改起来就会互相打脸。所以这一轮不是"再补几张表"，
而是把手上的四个问题**拆开各管各的**。

## 二、四个问题，四把尺子

```
职业（是什么活）        ← occupation 轴，一律登记，不设门槛
承接通道（谁付钱）      ← access 字段：paid_direct / non_market / org_internal / household
视角（在哪根轴成立）    ← axes 字段：同一分区可被多根轴引用，不是复制多份数据
单元（要不要建执行体）  ← status 字段：covered / pending / evaluated
```

关键改动：**`evaluated` 不再等于"忽略"**。

- 职业照样登记在 `industry-occupations.yaml`；
- 画像照样统计（`access_mix`、就业人数、付费方）；
- 产值照样计入产出轴；
- 只是不从"数字员工单元"这条产品线建单元。

这样"采矿工该不该被分析"和"要不要给采矿工建 AI 单元"就彻底分开了 ——
前者是数据问题，后者是产品问题。

## 四、新增的两根尺子

### `access`（职业）· 承接通道

| 值 | 含义 | 例子 |
|---|---|---|
| `paid_direct` | 服务本身直接收费（**缺省，不写即此值**，老数据零回填） | 架构师、会计、律师 |
| `non_market` | 财政/公共预算供养，终端用户不付费 | 军人、消防、矿工、政务窗口 |
| `org_internal` | 企业内部职能，需求侧是雇主预算 | 行政、前台、薪酬核算 |
| `household` | 家庭内部无酬劳动 | 家务、照护家人 |

实测分布（169 个已挂分区职业）：`paid_direct 88.8% / non_market 10.1% / org_internal 0.0% / household 1.2%`。

`non_market` 这个词是刻意选的：**它说明"不经过现金市场"，不是"没有价值"**。
财政本身就是购买力，只是采购通道不同。

### `axes`（分区）· 视角

`occupation` / `industry` / `tax` / `output` 四根轴，一个分区可以同时在多根轴下出现。
缺省 = 四轴都可见（老数据零回填）。收窄的只有三个职能型分区：
`admin-office` / `public-affairs` / `international-org` → `[occupation, output]`
（没有独立行业口径，也没有市场税目口径）。

**多视角 ≠ 多分区**：不是给每个视角复制一份数据，而是一份数据被多根轴引用。
分区 id 仍然唯一，`validate()` 第 16 条会拦住空 `axes` 和未知轴。

### `employment`（分区）· 产出轴补另一半

产出轴之前只有 `gdp_cny`，于是"有人没产值"的分区（军队、家庭无酬）在产出轴上
看起来是空的。现在每个分区都带 `employment`（万人）+ `employment_source`：

- 0 与"没口径"必须分开 → 没口径留空（null），填 0 会被 `validate()` 第 17 条拦下；
- 合计 56,480 万人（量级估算，含口径重叠，只用于看相对规模）。

## 五、错误折叠：把不同的东西捏成一个（本轮修）

用户报的两个 bug，本质是同一类错的两面：**把粒度/规则不同的对象折进一个容器，
合并之后就再也拆不出来**。

### 1. 规则不同却被折叠

| 原分区 | 拆成 | 为什么必须拆 |
|---|---|---|
| `translation` 翻译本地化 | `interpretation` 口译服务 / `translation` 翻译本地化 | 同传是**现场同步交付**，按场计费、资质门槛高，AI 替代面远低于笔译；混在一起"AI 替代率最高"的结论会套到同传头上 |
| `esports-live` 电竞直播陪玩 | `live-streaming` 直播与网络表演 / `esports` 电竞竞技 | 直播卖**打赏+品牌坑位**，电竞卖**奖金+俱乐部工资+票务+陪玩抽成**；共用一份"2000 亿"等于把两种商业模式捏成一个 |
| `sport-leisure` 体育健身 | `sport-fitness` 体育健身 / `sport-games` 赛事与场馆运营 | 面个人的课时制服务 vs 面机构的项目制；付费方、用工形态、计费方式全不同 |

拆完**不是把分母做大就完事**：产值口径没有独立发布，就留 `null` 并写明为什么，
不按比例从原合并口径里切一份出来（切一份等于同一批钱算两遍）。
`test_split_partition_gdp_is_not_double_counted` 守这条。

### 2. 层级不同却被折叠

分区表里一度出现 `sport-leisure` 这种 id —— 看着像行业，实际是把"健身教练/体育经纪/
赛事运营/场馆运营"几个岗位摞成一个筐。这是**把岗位当行业**：层级一错，后面
"这个行业的付费方是谁"根本没法答，因为筐里每个岗位的付费方都不一样。

现在两道守卫：

- `test_occupation_level_and_industry_level_ids_do_not_collide`：职业 id 与分区 id
  不得撞名（撞名会让反查串线、覆盖分子分母互相污染）
- `test_partition_name_is_not_a_job_title`：分区名不得正好是某个岗位名

另外新增 `test_folded_partitions_are_gone`：旧折叠 id（`esports-live` / `sport-leisure`）
一旦复活立刻红 —— 拆分最怕的不是拆不完，是下一轮合并又被悄悄撤销。

### 3. 连带修掉的显示 bug

中文长分区名（`国际组织与对外事务`）把表格顶歪：`'{: <14}'` 和 `str.ljust`
都按**字符数**补空格，CJK 字符占两列。改为 `_cell()` 按显示宽度定宽，
超宽截断加 `…`。`test_render_aligns_columns_for_cjk_names` 逐行校准列起点。

## 六、命令与接口

```bash

python3 src/hanghang/cli/main.py industry axis output
python3 src/hanghang/cli/main.py industry axis tax
python3 src/hanghang/cli/main.py industry axis            # 全景

# 承接通道：谁不靠终端用户付费，以及为什么这不是"没价值"
python3 src/hanghang/cli/main.py industry access
python3 src/hanghang/cli/main.py industry access --side non_market
python3 src/hanghang/cli/main.py industry occupations --access household
```

导出侧同步：`partitions.csv` 增加 `access_*` 四列、`employment_wan`、`axes`；
`occupations.csv` / json / sqlite 增加 `access` 列（缺省值也显式给出，便于下游直接聚合）。

`GET /api/industry-db` 的 `meta` 增加 `access_mix` / `access_mix_n` /
`employment_total_wan` / `employment_known_partitions`，分区行增加
`access_mix` / `employment` / `axes`。

## 十、留在桌面上的

1. **`access` 目前是人工判断**。军人/矿工/家务这几类没有争议，但"平台骑手算 paid_direct
   还是 org_internal"是灰区（付费方是消费者，结算方是平台）。要不要按"最终付款人"统一口径，需要拍板。
2. **`employment` 全是量级估算**，来源写在 `employment_source`，置信度不高/高都有。
   要对外用必须换成统计年鉴口径。
3. **主播/陪玩的付费结构**（打赏 vs 佣金 vs 工资）在 `billing` 里压成了一个值，
   这个行业其实是复合计费。要不要允许多值 `billings: []`，等下一轮。
4. 二级聚类（制造业拆电子/机械/化工）和 `gdp_cny` 逐年校准，本轮没动。
