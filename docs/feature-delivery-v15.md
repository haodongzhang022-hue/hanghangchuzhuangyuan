## 2. 产值口径标签（`gdp_kind` + `gdp_confidence`）

`gdp_cny` 旁边现在永远跟着口径类型，两者**同列**——分开存的话，总有人 `sum(gdp_cny)`
时忘了 join 口径。

| `gdp_kind` | 含义 | 能加总吗 |
|---|---|---|
| `value_added` | 增加值（GDP 口径） | ✅ 可相互加，可与统计年鉴对表 |
| `gross_output` | 总产值/总产出（含中间投入） | ⚠️ 会重复计算 |
| `revenue` | 营业收入/行业收入 | ⚠️ 含中间投入 |
| `market_size` | 市场规模（第三方测算） | ⚠️ 范围常与统计口径不同 |
| `cost_total` | 成本总额（物流费用/R&D 经费） | ❌ 本身是投入不是产出 |
| `gmv` | 交易额/流水 | ❌ 非增加值 |
| `none` | 无市场口径 | 不参与任何加总 |

现实分组（`industry partitions` 末尾直接打出来）：

```
value_added     6 个分区有数  合计    55.0 万亿元  置信度 高4/中2/低0
gross_output    5 个分区有数  合计    41.6 万亿元  置信度 高1/中3/低1
cost_total      3 个分区有数  合计    29.5 万亿元  置信度 高1/中2/低0
revenue        12 个分区有数  合计    25.1 万亿元  置信度 高1/中9/低2
gmv             2 个分区有数  合计    17.0 万亿元  置信度 高1/中0/低1
market_size     7 个分区有数  合计    13.6 万亿元  置信度 高0/中5/低2
none            6 个分区（刻意留空，不参与加总）
```

**可对外引用的只有 55.0 万亿。** 旧版 181.7 万亿里，15 万亿是电商 GMV、
18 万亿是物流总费用（成本，不是产出）、32 万亿是建筑业总产值（含中间投入）。
每个数都抄对了，加起来完全是另一回事 —— 这类错最难被发现，因为数字越大越像真的。

`gdp_confidence` 三档写清：`high` 官方统计直接可取 / `medium` 官方总额按分项拆分或行业
年报 / `low` 第三方测算。低置信的数可以排序定权重，**不许对外引用**。

新增**第 20 条校验**：有产值必须标口径、无产值必须标 `none`、数字与标签互相矛盾要报、
`gdp_confidence` 拼错要报。守卫用例 `test_industry_import_m11.py`（13 项）。

## 3. 结构单源 + 导入产物

`engine/industry_schema.py` 把「表长什么样」写成一份 `TABLES`：DDL、INSERT 列序、
行数断言全从它派生。此前手写在 CLI 里的那段 `CREATE TABLE` 有四个毛病：
只有 SQLite 方言、列顺序靠 tuple 位置对齐、加一列要改三处、漏一处就静默错位。

产物从 4 份变 7 份：

| 文件 | 用途 |
|---|---|
| `industry-db.json` / `partitions.csv` / `occupations.csv` | BI / 知识库直接吃 |
| `industry.sqlite` | 单文件库，拿到即用 |
| `00-schema.sqlite.sql` | SQLite 建表 |
| `00-schema.postgresql.sql` | PG 建表（同表同列，`REAL` → `DOUBLE PRECISION`） |
| `10-data.sql` | 数据，**与方言无关** |

```bash
# SQLite
sqlite3 hanghang.db < data/db/industry/00-schema.sqlite.sql
sqlite3 hanghang.db < out/industry-db/10-data.sql
# PostgreSQL
psql -d hanghang -f data/db/industry/00-schema.postgresql.sql
psql -d hanghang -f out/industry-db/10-data.sql
```

数据 SQL 只用标准写法：不写 `AUTOINCREMENT`、不用反斜杠转义单引号（MySQL 扩展，
SQLite 与 PG 都不认）、不依赖 `PRAGMA`。一份数据两种方言共用，不会出现「给 PG 维护了
第二套转义、结果两边字符不一样」这种最难查的错。

**结构进版本库、数据不进**：结构是契约，改一列要评审、要能被下游看见；数据从 yaml
秒级重建，把 1.6 MB 生成 SQL 提交进 git 只会得到看不见的 diff，改一次数据冲突一次。

## 4. CI 不再只看「文件非空」

`scripts/export_industry_db.py --check` 两件事：

1. 提交的 DDL 与代码单源是否一致（改了字段忘了重生成 → 红）；
2. **真灌一份临时 SQLite 再读回行数**逐表比对。

第 2 条才是关键：占位符个数与列数不匹配、转义写错、外键顺序颠倒，文件都照样非空。
PR 检查与 main 全量回归各挂一条。

## 6. 留在桌面上的（Issue #30 剩下的两条主线）

1. **二级聚类**：制造业 33 万亿、建筑工程 32 万亿、物流 18 万亿，一级分区对路由没有
   指导意义（电子 vs 机械 vs 化工）。需要设计 `parent_id` 二级机制，职业仍挂叶子分区
   以避免重复计数。**这件事影响库结构**，导入后要改表，建议导入前定下来。
2. **逐年对齐国家统计局**：现在口径标签是人工判读 + 行业报告，`gdp_year_basis` 统一写
   `2023-2024`。真要对外发布得逐年、逐分项对表，`gdp_confidence` 才配升级成 `high`。

另：`employment` 仍是量级估算，来源写在 `employment_source`，置信度不高。对外用要换统计年鉴。
