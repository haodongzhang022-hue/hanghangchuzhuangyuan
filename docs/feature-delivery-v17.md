## 一、盘存：东西都在哪，一句话能查

上一轮结束时，数据散在 11 份 yaml、5 份 DDL、10 份导出产物里，
"哪份是权威源、哪份是产物、平台落在哪"只存在于几个人的记忆里。
记忆会过期，而过期的清单比没有清单更坏——它让人相信某份文件还在被用。

所以盘存做成了**生成物**：

```bash
python3 scripts/gen_data_inventory.py            # 重生成
python3 scripts/gen_data_inventory.py --check    # CI：产物与数据不许分叉
```

产物两个，都是一眼能看的位置：

| 路径 | 用途 |
|---|---|
| `docs/industry/data-inventory.md` | 进版本库，被知识库切成片段（`**/*.md`） |
| `out/industry-db/data-inventory.csv` | 进导出产物，BI / 交接直接用 |

清单里四段：**权威源**（改数据只改这些）→ **结构产物**（DDL 进版本库，是契约）
→ **导出产物**（不进版本库，秒级重建）→ **库里的行数**（导出时实测）。
末尾还给「四本账各守什么」和平台路径（仓库 / 知识库 / 库）。

写的时候踩到两个小坑，都顺手钉住了：

- **`csv.writer` 默认 `\r\n`**，而 `--check` 读回来是归一化后的 `\n`。
  一个「永远过期」的守卫比没有守卫更坏——所有人都会把它关掉。改成
  `lineterminator="\n"`。
- **"读不出来"不能显示成 `0`**。`industry-classes.yaml` 顶层是 `!include`
  汇总入口、`rolecard-schema.yaml` 顶层是契约元信息，它们本来就没有条目数。
  显式显示「不适用（契约/索引文件，非条目）」，而不是一个看起来像真的 0。

## 二、逐年对表：`high` 从自我声明变成可核对

### 问题

`gdp_confidence: high` 原来是一句**自我声明**。谁都可以标 high，没人能证明。
于是"可对外引用"这四个字没有落点——它取决于当初填表那个人的心情。

### 做法

新增 `data/industry-official-baseline.yaml`：官方表值**按年存** + 分区↔基准的
对表关系。

```
benchmarks  17 个基准 × 逐年 series（16 个有两年以上，够算同比）
links       14 个分区接了官方口径
unlinked    27 个分区按组分说明为什么没有可比口径
```

三种关系，刻意只有三种：

| relation | 含义 | 比什么 |
|---|---|---|
| `equal` | 分区范围 = 官方范围 | 偏差 `\|分区-官方\|/官方 ≤ 10%` |
| `envelope` | 分区 ⊆ 官方（官方是门类总量） | 上界 `分区 ≤ 官方×1.1` |
| `incomparable` | 两者口径不同，**不能相减** | 只登记关系，不做数值比较 |

`incomparable` 不是偷懒的出口：它必须写 `reason`，**且该分区不得标 high**。
软件研发 6 万亿（软件业务收入，工信部）对信息服务业增加值 5.5 万亿（统计局），
收入必然大于增加值，相减得到的"差额"没有经济含义。这类关系必须显式写下来，
否则下一个人一定会拿它当"漏了 0.5 万亿"。

### 年份为什么不能硬取

分区原先只把年份写在 `gdp_year_basis: "2023-2024"` 这个自由文本里，机器读不到，
"逐年对齐"就无从校验。现在 `part_year()` 三级取值：

1. `gdp_year`（显式钉死）→ `declared`
2. `gdp_year_basis` 区间，**在基准已有年份里**取末年 → `basis_range`
3. 都没有 → `None`

第 2 条里的「基准已有」是关键。区间写 2023-2024、基准只录到 2023 时取 2023，
而不是硬取 2024 —— 硬取会得到「官方没这一年的数」，那看起来像"对不上"，
其实只是我们的基准还没录。`year_source` 把「这个年份是声明的还是推出来的」
一路带到对表结论里，推出来的年份不会被当成声明过的。

### 机制一上线就抓到三处错

这是最值得记的一段：对表**不是**写给人看的表格，它在生效的第一次 `industry check`
里就报了三处：

| 报出 | 真相 |
|---|---|
| `agriculture` 偏差 −90.0% | `va-primary` 双手一抖多写一个零（88.2 万亿 vs 实际 8.8 万亿） |
| `mining-resources` 标 high 但没有对表 | 当初凭印象写的 high |
| `utilities` 标 high 但没有对表 | 同上 |

第一处是纯录入错，但它**单看是对的**（88 万亿确实像"农林牧渔总产值 + 加工"），
只有和分区那 9 万亿一撞才现形 —— 而这正是对表要抓的那类错。
第二三处直接把「high 是自我声明」这句话演示了一遍。

补了两个门类基准（`va-mining`、`va-utilities`）之后，`utilities` 又报偏差 −13%：
原来分区的 4.0 万亿比官方 4.6 万亿少了 6 千亿。改数、补 `gdp_year: 2023`。

现在：**对上 12 / 不可比 1 / 无该年表值 1 / 没接但已说明 27 / 没接又没说明 0**。

## 三、生产法：切分不重复计的规则

上一轮末尾写着：

> 8 个池的流入数额全待补，卡在「中间投入怎么去重」——不是拿不到数，是拿了会重复计。

这轮的答案就是生产法恒等式：

```
总产出 = 增加值 + 中间投入
```

### 为什么不能拿营业收入当增加值切分

部门层的总额是**增加值性质**（收入法 GDP）。而分区手里的数：

```
电商 15 万亿      GMV，平台两头各计价一次
软件研发 6 万亿   软件业务收入，含中间投入与硬件
建筑 31.6 万亿    总产值，含分包重复报量
```

拿这些去切部门总额，切出来的份额必然虚高 —— 而且虚高得看不出来，
因为每个数都抄对了。所以切分锚点只有两条合法路径：

1. 分区本来就是 `value_added` 口径 → 直接可切
2. 分区是 output/revenue/GMV → 必须先有 `va_ratio`（增加值 ÷ 总产出）折算

**没有 `va_ratio` 就不许切。** 宁可留 `null`，也不按比例摊一份 ——
摊出来的份额看起来合理，实际上是错的，而错的数一旦进库，后面所有人都会当实测用。

### 现在的产出

```
账户 35 个：恒等式闭合 1 / 只够一端 8 / 还没有落点 32 / 对不上 0
行业池 8 个：可切 2（manufacturing、construction-eng）/ 不可切 6
```

建筑业是样板，三端全有官方出处，恒等式闭着：

```
总产出   31.6 万亿 = 增加值 8.6 万亿 + 中间投入 23.0 万亿
va_ratio 0.272 —— 每 100 元产值里只有 27 元是新增价值
```

这句话就是「拿 31.6 万亿去和增加值口径的分区并列排序会高估 3.7 倍」的量化版。

制造业则演示另一半：**增加值有、总产出没有**。规上工业营业收入是「工业」门类
（含采矿、电力热力燃气水），直接当制造业总产出会把两个门类混成一个。
所以 va_ratio 算不出来 —— 这就是「33 万亿怎么切到 40 万个规上企业」卡住的真实原因，
不是数据源没找到，是缺总产出这一端。

### 三处不得重复计（第 25 条校验）

| 守什么 | 为什么 |
|---|---|
| 中间投入构成合计 = 总额（声明 `complete` 时） | 同一件事存两份，迟早一边改了另一边没改，而没人知道哪份是对的 |
| 某分区作为投入方出现在别人 `inputs` 里的合计 ≤ 它自己的总产出 | 供不出比自己产出更多的东西。这是"去重"的关门条件 |
| 所有分区增加值合计 ≤ 全国 GDP | 超了必然是同一笔价值被两个分区各算了一遍 |

第三处的分母从 `gdp-total` 基准借，不在账里抄第二份 —— GDP 每年修订，两处各存
一份时，跑对账的人和跑汇总的人会拿到两个不同分母，而且没人知道哪个对。

## 四、一个必须单独讲的坑：`allocation` 是备忘边

给池填上锚点之后，立刻撞上一个真问题：

```
sector-enterprise → pool:manufacturing  allocation  33.0 万亿
```

这条边如果计入企业部门的流出，流出就从 110.1 万亿变成 143.5 万亿，
偏差 30% 直接爆红 —— **而两条记录各自都是对的**。

原因是语义混了：制造业 33 万亿增加值**本就含在**企业部门那 110.5 万亿里。
`allocation` 不是新发生的一笔钱，它是把已有总额**摊开看**。

所以加了 `memo` 语义：

- `allocation` 一律 `memo: true`，validate 强制（写错方向也报：把 `wage` 标成
  memo 会静默漏掉一笔真钱）
- memo 边不进 `position()` 的流入流出，单独计 `memo_edges`
- `amount_coverage` 分母只算真实流。备忘边本来就没数额，算进分母会让
  「图画完了多少」这个数永远上不去，于是没人再认真看它
- 落库到 `money_flow.memo` 列，扁平表 `money-flows.csv` 也带这一列 ——
  下游一句 `SUM(amount_cny) WHERE memo=0` 才算得对总资金量

修完之后：**真实资金流 19 条全都有数额（图完整度 100%）**，
备忘边 8 条 0 填（份额还没算，这是对的）。

## 七、还没做的

1. **`gdp_year` 只有 `utilities` 一个写了**。其余 40 个分区的年份仍靠
   `gdp_year_basis` 区间推。要让"逐年对齐"名副其实，得逐分区把年份钉死到
   **它自己那份数的发布年**（不同数据源不同年，区间只是兜底）。
2. **`series` 只有 2022/2023 两年，且大部分标 medium**。统计局年鉴与初步核算
   有 1-3% 修订差，要对到 `high` 得逐年逐分项抄表值 —— 这是纯工作量，不是机制问题。
3. **投入产出表的中间投入构成还没接**。现在是 0 个分区有 `inputs`，
   建筑业那 23 万亿只知道总额、不知道切成建材/机械/分包各多少。
   接进 149 部门投入产出表之后，`complete: true` 那条校验才真正开始干活。
4. **27 个分区没有官方可比口径**。分组说明已经写了（专业服务没有独立增加值、
   财政口径没有市场化产值、门类范围与分区不对应），但每一组都要等口径能一对一
   映射才能接——这条是长线，写在 ISSUE #30 的待办里。
5. **池份额还没算**。可切的 2 个池拿到了锚点，但 `allocation` 的金额仍是 null：
   切分还要决定"部门总额按什么比例分给两个池"，而两个池加起来 41.6 万亿
   对不上企业部门任何一项真实流入。这条得等中间投入构成接进来才有意义。
