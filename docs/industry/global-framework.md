# 全球分类框架：四根轴，一套可往下填的结构

> 这份文档回答一个问题：**别人是怎么给"行业和职业"立规矩的，我们该照着谁立。**
>
> 结论先放前面：世界上没有"一套全的分类"，只有**四根互不正交的轴**。
> 把轴分清楚，才谈得上"补充内容"；轴混在一起，补得越多越乱。

## 一、四根轴，别混着用

| 轴 | 问的问题 | 权威体系 | 我们不做什么 |
|---|---|---|---|
| 职业 | 这个人在干什么活 | 中国大典 2022 / ISCO-08 / SOC / O*NET | 不拿行业名当职业名 |
| 行业 | 这家单位在卖什么 | GB/T 4754 / ISIC / NACE / NAICS | 不把职业清单塞进行业 |
| 税收 | 这笔钱按什么税目征 | 增值税税目 / OECD / EU VAT | **不拿税目当行业码** |
| 产出 | 一年多大产值、多少人 | 统计局增加值 / ILOSTAT / OECD STAN | 不编造没有口径的数字 |

为什么税收必须单列：同一行业里不同税目税率不同（软件产品 13%、技术服务 6%），
同一税目跨行业。**税率跟"卖的是什么"走，不跟行业走。** 把它塞进分区表，
一次税率调整就会污染整张聚类表。

## 二、国外有没有这类规则：有，而且比我们想的更细

按"能不能直接拿来用"排序：

### 1. ISCO-08 —— 职业轴的国际母版（已接入 ✅）

- 维护：ILO。10 大类 / 43 次大类 / 130 小类 / **436 细类**。
- 编码：`2512` Software developers。位数即层级，短码是长码前缀。
- 它是美国 SOC、英国 SOC、ANZSCO、加拿大 NOC、德国 KldB 的**表头**。
  这些国家分类第一层就是"按 ISCO 对齐"。
- 我们落了什么：`data/reference/occupation-catalog-isco08.yaml`，
  436 个细类全带官方描述 + **1931 条官方示例职位名**。
  示例名是这套表最值钱的部分——"这个工种在英文里到底叫什么"直接查得到，
  不用凭印象翻译。

> 一句话：大典告诉我们国内怎么分，ISCO 告诉我们国际上这个职业归哪一类。

### 2. SOC + O*NET —— 职业轴的量化层（待接 ⏳）

ISCO 只说"职业叫什么"，SOC/O*NET 说"这活要什么技能、多少人在干、挣多少、
未来十年是涨还是跌"。O*NET 923 个职业，8 类描述符（技能/知识/能力/工作活动/
工作情境/工作价值观/兴趣/工作风格），**CC BY 4.0 可商用**。

这是我们最缺的一块：现在 `provider: ai/hybrid/human` 是拍脑袋标的，
O*NET 的任务清单 + AI 暴露度研究（AIOE、GenAI exposure）才是外部校准依据。

### 3. ISIC / NACE / NAICS / GB/T 4754 —— 行业轴（待接 ⏳）

| 体系 | 层级 | 谁维护 | 对我们的用处 |
|---|---|---|---|
| GB/T 4754-2017 | 20 门类 / 97 大类 / 473 中类 / 1380 小类 | 国家统计局 | **优先**：对得上税务和统计口径 |
| ISIC Rev.4 | 21 / 88 / 238 / 419 | 联合国 | 跨境比较的公共语言 |
| NACE Rev.2.1 | 21 / 88 / 284 / 654 | Eurostat | 与 ISIC 同源，接了 ISIC 基本免费 |
| NAICS 2022 | 20 / 99 / 320 / 1046 | 美加墨 | 新兴服务分得清，6 位码好用 |

接的顺序：**GB/T 4754 → ISIC → NAICS**。先能对上税务局和统计局，
再谈国际比较。反过来先接 NAICS，等于给一堆对不上国内口径的码。

### 4. 税收口径（待接 ⏳）

- 国内：增值税税目（货物/服务/无形资产/不动产）+ 税率档 13/9/6/3/1/0；
  外加企业所得税行业优惠目录、研发费用加计扣除行业范围。
- 跨境：OECD 税收数据库（宏观税负比对）、EU VAT 指令（数字服务 VAT 注册地规则）、
  各国数字服务税（DST）。
- **它不进聚类依据**，只作为成本与定价参考。分区聚类理由仍然是"谁付钱 + 交付物"。

## 三、接法：新轴先落"参考表 + 映射表"，不直接改主库

已经跑通的模式（大典就是这么进来的，照着复制）：

```
data/reference/<标准>-catalog.yaml     ← 标准原文，只读，换版整份替换
data/reference/<标准>-<我们>.yaml      ← 人工核对的交叉映射，宁缺勿错
data/industry-*.yaml                   ← 我们自己的执行口径，字段只加不改
```

为什么必须先落参考表：

1. **可 diff、可评审、可回滚**。直接改主库，改错了没人看得出来。
2. **换版代价低**。2015→2022、Rev.4→Rev.5、SOC 2018→2028，整份替换参考表，
   映射表才是需要人工过一遍的地方。
3. **不稀释分母**。外部全集（1636 / 436 / 1380）永远不进 coverage 分母，
   否则覆盖率会被稀释成没意义的数字。

字段落位（下一轮要做的）：

| 轴 | 参考表 | 挂到哪 | 字段名 |
|---|---|---|---|
| 职业 | ISCO-08 ✅ / SOC / O*NET | `industry-occupations.yaml` | `isco_code` / `soc_code` / `onet_code` |
| 行业 | GB/T 4754 / ISIC | `industry-partitions.yaml` | `gb_industry_code` / `isic_code` |
| 税收 | 增值税税目 | 新表 `tax-items.yaml` | `partition.tax_items[]` + `occupation.billing_tax` |

## 四、优先级：先补哪一层

不是所有格子都值得填。判断标准只有一条：**能不能改掉一个具体判断。**

| 顺序 | 做什么 | 为什么先做这个 |
|---|---|---|
| P0 | 职业挂 ISCO 细类码（人工核对，宁缺勿错） | 跨境对齐、英文命名、海外招聘三件事一次解决 |
| P0 | 分区挂 GB/T 4754 行业码 | 对得上税务与统计局口径，产值才有校准依据 |
| P1 | 职业接 O*NET 任务/技能维度 | `provider` 从"感觉"变成"有依据" |
| P1 | 税目表（税率档 + 对应交付物） | 报价、成本、承接边界都要它 |
| P2 | ISIC / NAICS 交叉表 | 国际比较用，非必需 |
| P2 | 产值逐年校准 | 现在 gdp_cny 是量级估算，只能排序不能对外 |

## 五、已经能查的东西

```bash

```

## 六、这几条别破

1. **外部标准只读**。补职业、改聚类不许动参考文件。
2. **外部全集不进分母**。1636 条、436 条都是"还能挑多少"，不是"还欠多少"。
3. **交叉映射人工核对**。错挂比不挂坏得更彻底——挂上之后反查、导出、统计
   全跟着错，而且没人会再看第二遍。
4. **税目不是行业码**。一根轴一个字段，混装等于给未来的自己挖坑。
5. **没有口径就不填数字**。`gdp_cny: null` 比编一个"大概几万亿"诚实得多。
