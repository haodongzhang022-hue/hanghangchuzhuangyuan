# 评审修复闭环护栏

> 本文件定义 hanghangchuzhuangyuan（通用能力层）的自动评审机制规则。
> 机制设计参考自 dongjiagoushi（架构师团队）与 youxikaifaxilieagent（游戏开发）的自动评审闭环。

## 一、机制总览

```
PR 提交 → 测试信号灯 → NPC 代码审查
                          │
              ┌───────────┴───────────┐
              │ 需修改                │ 通过
              ▼                       ▼
  评审NPC 全限定名召唤修复       合并门禁
              │                       │
              ▼                       ▼
  CodeBuddy 修复+提交 → 新commit → 自动合并
              │       重新触发 pull_request → 下一轮审查
              │
        （目标导向循环：有错继续修，无错即停）
```

## 二、触发源

| 触发源 | 事件 | 触发动作 |
|--------|------|----------|
| PR 提交/更新 | `pull_request` | 测试信号灯 + NPC 代码审查 |
| 评审发现需修改 | 评审结论里召唤（全限定名） | 自动触发 CodeBuddy 修复（**主通道**） |
| 评审通过 | `pull_request.approved` | 重跑检查 + 自动合并 |
| 评审正式打回 | `pull_request.changes_requested` | CodeBuddy 自动修复（**兜底**，与主通道二选一） |
| PR 评论召唤 | `pull_request.comment@npc` | CodeBuddy 处理（人类/评审NPC均可触发） |
| main 合并 | `main.push` | 全量回归 + 知识库更新 |

### 召唤写法只有一种

`@dongdongxiaozu/hanghangchuzhuangyuan(CodeBuddy)` —— 全限定名，带仓库路径。

只写 `@` 加角色名（不带仓库路径）命中的是**平台系统 NPC**：它不读本仓库
`.cnb.yml`，按系统默认配置起机器（8 核），也不受本文件里任何护栏约束。
本仓库 2026 年 9–11 月的实测账：

| 召唤写法 | 次数 | 核时 |
|---|---:|---:|
| 带仓库路径（走本仓库配置） | 72 | 27.0 |
| 只写角色名（平台系统默认） | 144 | 268.3 |

同样的事差 10 倍。2026-11-15 PR #34 的 CI 连红在 Prepare，报
`Core CPU core-hours are insufficient for pre-freezing`；当月累计已用 274.6 核时，
而免费额度是 160 核时/月。缺口的大头就是这张表的第一行之外那部分。

守卫在 `tests/test_industry_completion.py::test_pipeline_prompts_never_summon_bare_codebuddy`。

### 两条修复通道不许同时开火

| 通道 | 事件 | 定位 |
|---|---|---|
| 主 | `pull_request.comment@npc`（评审结论里召唤） | 正常路径 |
| 兜底 | `pull_request.changes_requested` | 召唤那一路没发生时兜住 |

同一次打回同时走两条，就是**两个修复 Agent 在同一分支上改同一批文件**，
各烧一份配额。实测 29 次打回里 22 次都和一条召唤会话在同一分钟内起跑
（间隔 ≤3 min），11 月这条通道烧掉 80.1 核时，几乎全是重复。

所以评审员的纪律是**二选一**：召唤了就不再提交打回，打回了就不再召唤。
守卫在 `tests/test_industry_completion.py::test_review_prompt_forbids_double_dispatch`。

### 每条流水线都写 `runner.cpus: 1`

不写就是 8 核（平台默认节点规格），冻结量按节点规格算，与真实用量无关。
本仓库所有 job 都是串行 python 测试或等 AI 接口，多核不被使用却照样烧额度
（实测单个测试文件单进程跑 47–95 s，全量 37 个文件 470 s）。

守卫在 `tests/test_industry_completion.py::test_every_pipeline_declares_its_own_runner_size`。

### 护栏要写在**生效的那份文件**里

上面三条（全限定名、二选一、`runner.cpus`）最初都写在 `.cnb.yml` 的
`pull_request.comment@npc` 里 —— 那是不生效的位置。官方 `npc:go` 文档「提示词配置」写明：

> `@NPC` 评论触发时，平台按 `.cnb/settings.yml` 中的角色定义注入提示词，
> 你无需配置，即使配了 `systemPrompt` / `userPrompt` / `role` 也会被忽略。

所以真人或评审 NPC 一召唤，跑的是 `.cnb/settings.yml` 里那段 prompt，
`.cnb.yml` 里写的纪律一条都不进模型。**而断言还一直是绿的**，
因为它查的也是 `.cnb.yml`。

> 断言写在错的文件上，与没有断言是同一种下场，只是多了个绿灯。

现在纪律两边都写，并新增断言
`test_npc_role_prompts_carry_the_same_discipline` 专门查 `.cnb/settings.yml`。

### 配额类红灯不许召唤修复

失败 Stage 是 `Prepare`、报错含 `insufficient` / `pre-freezing` / `core-hours` 时，
红灯不在代码里。这时召唤一个代码修复 Agent，它只会读代码、跑全量测试，
一小时后回一句「跟代码无关，是组织配额见底」——**每小时 8 核时，产出为零**。

PR #34 就有两次这样的完整回放。所以纪律是：

- 评审员：写出报错原文 + 一句「组织 CPU 额度见底，需提额」就结束，不召唤；
- 修复者：`Prepare` 类红灯不读代码、不跑测试、不重试，只做上面那条；
- 人类：这类红灯只有提额或等下月能解，改代码改不好它。

### 两条修复通道共用一把锁（机制，不是自觉）

`auto-fix`（`changes_requested`）与 `npc-manual-invoke`（`comment@npc`）现在共用

```yaml
lock:
  key: npc-fix-$CNB_PULL_REQUEST_IID
  cancel-in-progress: true
```

提示词里写「二选一」是自觉，lock 是机制 —— 自觉会忘，机制不会。
`cancel-in-progress` 的意思是后到的取消先到的：两条做的是同一件事（在同一分支改同一批评审点），
排队的意义不大，而排队期间它照样占着预冻结额度。
key 里带 PR 编号，避免把不同 PR 的评审也串成一条队。

守卫在 `tests/test_industry_completion.py::test_npc_fix_channels_share_one_lock`。

## 三、角色职责

### 代码审查员（只读）
- 读取代码、审查质量/架构/Bug/安全
- 输出审查结论（通过/需修改）
- **发现问题必须**在结论中召唤修复（全限定名，见第二节），且与打回二选一
- **无写权限**：不 push、不 merge、不改代码

### CodeBuddy（修复执行）
- 收到评审意见（人类手动或评审NPC召唤）后默认直接修复
- 目标导向：修复到评审通过为止，有错继续修，无错即自然停止
- 安全上限：连续 5 轮仍未解决则停止，反馈人类介入
- 每修一个点尽量固化为测试断言
- 修复提交后自然触发下一轮评审（无需额外操作）

## 四、修复护栏规则

### 4.1 默认直接改
评审指出的问题（尤其 bug）默认应直接修复，不反复询问。

### 4.2 目标导向（核心原则）
**不是固定跑 N 轮**。评审无错即停，有错才继续。每轮修复提交后自动触发下一轮
评审，由评审结论决定是否需要继续修复，而非由轮数决定。

### 4.3 安全上限
同一 PR 的评审→修复来回最多 5 次。达到上限仍无法解决则停止自动修复，
在 PR 评论中反馈人类，由人类改需求/框架。

### 4.4 测试断言固化
每修一个评审点，尽量固化成测试断言，防止回退。

### 4.5 空修复检测
若评审"需修改"但未指出可定位的具体代码缺陷，或修改点与已提交内容一致
（无实际 diff），**禁止盲目提交/空转**，显式反馈人类说明"无实际可修复内容"。

### 4.5b 先判断红灯归谁（优先于 4.1「默认直接改」）
`Prepare` 阶段失败、报错含 `insufficient` / `pre-freezing` / `core-hours` 时，
这是组织额度见底，不是代码缺陷。此时**不读代码、不跑全量测试、不召唤、不重试**，
只贴报错原文 + 结论（需提额）+ 人类动作。空转一小时 = 8 核时 = 零产出。

### 4.6 钩子没 bug 就停
若评审结论为"通过/approved"，说明无 bug，直接结束本阶段，不再改动任何内容，
交由后续合并门禁处理。

### 4.7 评审 NPC 自动召唤修复
评审 NPC 在评审中发现问题后，**必须在结论末尾召唤**（格式：
`@dongdongxiaozu/hanghangchuzhuangyuan(CodeBuddy)`，必须带仓库路径），这会触发
`pull_request.comment@npc` 事件 → CodeBuddy 自动接管修复。
若评审通过（无问题），不召唤任何人，自然停止。
**召唤了就不再提交打回结论**——见第二节「两条修复通道不许同时开火」。
**配额类红灯（`Prepare` / `insufficient` / `pre-freezing`）不召唤**——见第二节。

### 4.8 禁止 push 的评审闭环
**本系统设计不允许评审NPC push**：评审闭环通过 PR 评论 + 事件驱动。
评审 NPC 只读不改；CodeBuddy 负责修复和提交（通过正常 git 流程在 PR 源分支提交）。

## 五、仓库身份自适应

CodeBuddy 在本仓库中的身份是：
`@dongdongxiaozu/hanghangchuzhuangyuan(CodeBuddy)`

跨仓库协作用完整格式召唤。评审中发现需要其他仓库配合调整时，到对应源仓库提 Issue。

## 六、评审结论统一格式

评审输出需包含：
- **结论**：✅ 通过 / 🔴 需修改
- **严重级别**：🔴必修 / 🟡建议 / 🟢优化
- **具体问题**：文件路径 + 行号 + 问题描述 + 修改建议
- **修复召唤**：发现问题时必须召唤全限定名（自动触发修复），且与打回二选一

## 八、这轮把配额算清楚了（2026-11-15）

「构建 CPU 消耗很大」不是抽象感受，可以逐条算出来。查完本仓库全部构建历史，
按 `cpus × 时长` 汇总：

| 浪费形态 | 实测 | 成因 |
|---|---:|---|
| 裸名召唤（系统 NPC） | 9 次 / **58.9 核时** | 命中平台系统 NPC，8 核默认规格，不读本仓库 `.cnb.yml` |
| 全限定名召唤（本仓库配置） | 1 次 / 2.4 核时 | 走 `runner.cpus: 1` |
| 配额红灯仍召唤修复 | 2 次 / 40+ 核时 | `Prepare` 红、一个测试没跑，仍起一台 8 核跑满一小时 |
| 两条修复通道并行 | 历史 22 / 29 次打回 | 同一分支、同一批评审点，改两遍 |
| 过期 commit 的审查跑完 | 单次 27~88 分钟 | 分支已更新，结论没人看 |

结论：**这不是 CPU 不够，是同一件事被做了两遍、或在一件必然白跑的事上等了一小时。**
四条对应四种改法（全限定名 / 配额红灯不召唤 / 共用一把锁 / `breakIfModify`），
每条都有断言钉住，改回去 CI 就红。

真正需要人类的只有一件：免费额度 160 核时/月已经用超，要向根组织申请提额
（`组织` → `设置` → `用量管理`，或绑定腾讯云预算）。配置层能做的已经做完，
剩下的不是配置能解决的。

## 九、"结构写歪"是另一层，不是"非数值"

前几轮把「非数值金额」守住了：写坏的数是字符串、是单位混写，都报成一句人话。
但评审六轮点出的是**另一层**：`(it or {})` 留不住形状错。

```python
for it in pools:            # pools 里混进一个 "字符串"
    where = (it or {}).get("where")   # AttributeError: 'str' object has no attribute 'get'
```

`(it or {})` 只兜得住 `None`。而**数据是人或模型手写的，列表里混一个字符串是
最常见的写法之一**。结果一样：`industry check` 自己 traceback，红灯既不是
"数据坏了"也不是"绿"。

更坏的是 `missing: "缺"` 写成标量 —— 它崩在 `_load()`，于是
`IndustryDatabase()` 构造就失败，`industry scale` / `strategy` / `baseline` /
`io` / `export` / `/api/industry-db` **全部一起挂**。一份只读旁证的形状错
连坐整个 M11 出口。

### 修法：入口收口，不在消费点各兜一次

`src/hanghang/engine/_shape.py` 三个函数（`dict_list` / `mapping` / `str_list`），
五本账的 `_load()` 一律走它们，写歪的项记进 `load_problems`，由 `validate()` 报。

| 做法 | 结果 |
|---|---|
| 每个消费点各写一次 `(it or {})` | 想到的路守住了，没想到的路照样崩 |
| **入口统一归一** | 只有一处要维护，且新增消费点自动受益 |

两条约定与这套账的既有立场一致：**不静默丢**（记一条 problem，不悄悄跳过）、
**不当成"没填"**（写歪要改数据，空着要补数据，两句话不能说成一句）。

### 顺带修掉的同类

| # | 形态 | 为什么它比报错坏 |
|---|---|---|
| 3 | `declared_*_cny` 为负 → `abs(gap)/declared` 是负数，永远 ≤ 容差 | status=ok、validate 一条不报。一个符号手滑关掉唯一能抓漏的那条对账，而负的偏差率看着像"略有偏差" |
| 4 | `declared = 0` 时 CLI 自己算 ratio 并打 ✓ | engine 早有 `declared_zero` 判词。同一条数据两个结论，人只会照着绿的那个看 |
| 5 | `money --node` 对 declared 做裸减法 | 同文件里 flow 金额已改用 `_num()`，声明口径那半边漏了 —— 修了一半 |
| 6 | `_input_amount` 的 `share` 分支两个出口都 `return None` | **按文档写数据反而报错**，比不支持更坏 |
| 7 | `RoleCardStore` 里的 `StrategyView` 没绑 partitions/registry | `_roles_of()` 回落 `planned_roles`，于是每张岗位卡都把合法落点报成悬空 |
| 8 | `to_context_block()` 的行业判断写在 `if p:` 里面 | 没有画像基线就静默丢行业判断 —— 而那条断言想表达的恰恰是"少了画像也不该少行业" |
| 9 | 提示语写 `industry strategy --gaps` | 真实入口是 `industry strategy-gaps`，照着敲拿 `unrecognized arguments` |
| 10 | `open(DOC).read()` 无 `with` | `-W error::ResourceWarning` 下告警，全仓唯一一处 |

守卫：`tests/test_scale_money_m11.py` 里 7 条负向用例，全部对着**写歪的数据**
（不是"非数值"，是"形状错"），且都反向验证过能红。
