# 评审修复闭环护栏

> 本文件定义 hanghangchuzhuangyuan（通用能力层）的自动评审机制规则。
> 机制设计参考自 dongjiagoushi（架构师团队）与 youxikaifaxilieagent（游戏开发）的自动评审闭环。

## 一、机制总览

```
PR 提交 → 测试信号灯 → NPC 代码审查 → 需修改？→ CodeBuddy 自动修复
                                              │           │
                                              │ 不需要     │ 修复后打标签触发下一轮
                                              ▼           ▼
                                        评审通过 → 合并门禁 → 自动合并
                                              │
                                              ▼
                                        main 合并 → 全量回归
```

## 二、触发源

| 触发源 | 事件 | 触发动作 |
|--------|------|----------|
| PR 提交/更新 | `pull_request` | 测试信号灯 + NPC 代码审查 + 修复闭环 |
| PR 可合并 | `pull_request.mergeable` | 测试确认 + 自动合并 |
| 人工评审打回 | `pull_request.changes_requested` | CodeBuddy 自动修复 |
| 人工评论 @CodeBuddy | `pull_request.comment@npc` | CodeBuddy 手动兜底 |
| 流水线失败 | `failStages` | CodeBuddy 自动诊断处置 |
| main 合并 | `main.push` | 全量回归 + 知识库更新 |

## 三、角色职责

### 代码审查员（只读）
- 读取代码、审查质量/架构/Bug/安全
- 输出审查结论（通过/需修改）
- 发现问题召唤 CodeBuddy 修复
- **无写权限**：不 push、不 merge、不改代码

### CodeBuddy（修复执行）
- 收到评审意见后默认直接修复
- 最大 5 轮护栏：同一 PR 评审→修复最多 5 次
- 每修一个点尽量固化为测试断言
- 修复完成后提交并召唤下一轮评审

## 四、修复护栏规则

### 4.1 默认直接改
评审指出的问题（尤其 bug）默认应直接修复，不反复询问。

### 4.2 最大 5 轮
同一 PR 的评审→修复来回最多 5 次，达到上限仍无法解决则停止自动修复，
在 PR 评论中反馈人类，由人类改需求/框架。

### 4.3 测试断言固化
每修一个评审点，尽量固化成测试断言，防止回退。

### 4.4 空修复检测
若评审"需修改"但未指出可定位的具体代码缺陷，或修改点与已提交内容一致
（无实际 diff），**禁止盲目提交/空转**，显式反馈人类说明"无实际可修复内容"。

### 4.5 钩子没 bug 就停
若评审结论为"通过/approved"，说明无 bug，直接结束本阶段，不再改动任何内容，
交由后续合并门禁处理。

### 4.6 禁止 push 的评审闭环
**本系统故意设计不允许 push**：评审闭环通过 PR 评论 + 标签驱动（如打标签触发
下一轮 pull_request 事件），任何 NPC **不得尝试 push**（会触发 403 报错、
破坏闭环），也不得在评论中输出 "push 失败 / 403" 这类错误尝试信息。

## 五、仓库身份自适应

CodeBuddy 在本仓库中的身份是：
`@dongdongxiaozu/hanghangchuzhuangyuan(CodeBuddy)`

跨仓库协作用完整格式召唤。评审中发现需要其他仓库配合调整时，到对应源仓库提 Issue。

## 六、评审结论统一格式

评审输出需包含：
- **结论**：✅ 通过 / 🔴 需修改
- **严重级别**：🔴必修 / 🟡建议 / 🟢优化
- **具体问题**：文件路径 + 行号 + 问题描述 + 修改建议
- **修复召唤**：发现问题时召唤 CodeBuddy 处理
